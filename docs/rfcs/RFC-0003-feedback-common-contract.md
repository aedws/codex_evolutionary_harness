# RFC-0003 — 자가피드백 공통 계약과 씨앗 반영

- 상태: contract 2 설계 기준. 자동 피드백 실행기 구현이나 인간 최종 수락 선언은 아님.
- 요구사항: REQ-HARNESS-FEEDBACK-001, REQ-HARNESS-CONTRACT-COVERAGE-001.
- 상위: [RFC-0002](RFC-0002-hierarchical-evolutionary-architecture.md).
- 규범: [F01–F07](../../seed/docs/harness/contracts/feedback.md), [E01–E06](../../seed/docs/harness/contracts/evolution.md), [X01–X05](../../seed/docs/harness/contracts/execution.md).

## 1. 해결할 문제

v0.1.0은 Project → Domain → Core 원칙을 담았으나, 오류 개선·스킬 사용의 관측 시점, 공유 가능한 후보, 업스트림 권한·중복 제출, 릴리스 후 원 프로젝트 효과 확인의 공통 계약이 부족했다. 에이전트가 좋은 개선이라고 서술하는 것만으로 씨앗이 바뀌거나, 각 프로젝트가 다른 절차를 발명하는 문제가 생긴다.

v0.2.0은 작업 종료 시 한 번의 검토부터 후보·평가·제출·승격·릴리스·재적용까지 연결한다. 호출마다 규칙을 늘리지 않는다. `no_candidate`도 정상 결과이며 검토는 이미 수집한 증거를 재사용한다.

## 2. 최소 재사용 산출물과 소유권

| 경로 | 역할 / 소유권 |
|---|---|
| `AGENTS.md` | 승인된 변경 작업의 종료 시 피드백 검토 의무; 프로젝트 지침과 명시적으로 통합 |
| `contracts/feedback.md` | 공통 절차; 원본은 릴리스로 관리 |
| `feedback/config.json` | 제출 대상·권한·공유·예산의 프로젝트 바인딩; 배포 때 빈 값 |
| `templates/*.example.json` | 작성용 예제; formal schema나 실행된 사실이 아님 |
| 프로젝트 Evidence/Event/Execution | 원자료·시도·결정·효과 기록; 다른 프로젝트에 복사하지 않음 |
| 업스트림 `proposals/` | 허가된 추상 후보만 수집; seed 배포 allowlist 밖 |
| `seed/` | 받아들인 공통 계약과 빈 바인딩만 배포 |

후보를 실제 레코드로 채울 때 ID, origin/base/digest, 원인과 불확실성, 변경, 평가, 공유 범위, 제출 영수증을 사실에 맞게 작성한다. 단계별 필수 근거는 F04–F07에서 판정한다. 예제의 빈 값이나 `template_only: false` 변경만으로 제출 가능 상태가 되지 않는다.

## 3. 오류와 스킬의 예시 경로

제품 오류를 수정하고 회귀 테스트를 통과시킨 경우, 제품에만 해당하면 project_bug 관측으로 끝낸다. 같은 실패가 테스트 선택 계약의 누락에서 반복되었다면 원인·기존 선택 결과·반례를 묶어 HARNESS-REQ 후보로 만든다. 새 계약을 동일 입력에 평가해도 로컬 결과만으로 universal로 승인하지 않는다.

스킬을 추가한 경우에는 출처·소유자·SKILL.md 및 사용한 자원의 digest, 선택 이유, 실제 실행 여부, 결과 근거를 구별한다. 적합/부적합 트리거 사례와 기존 workflow 의존을 검토한다. 특정 도메인 스킬의 성공을 전체 씨앗의 필수 스킬로 만들지 않는다. 공통 선택·검증 절차에 재현 가능한 결함이 있을 때 그 계약을 후보로 제안한다. 전역 또는 플러그인 관리 스킬을 프로젝트가 몰래 수정하지 않는다.

예시는 절차 설명이며 실제 실행 관측이나 승격 근거가 아니다.

## 4. 권한·재시도·되돌리기

기본 모드는 local-only다. 설치 영수증의 upstream URL은 출처이며 제출 권한이 아니다. 명시적으로 허용된 목적지·파일 allowlist·정확한 묶음 digest·권한 근거를 확인한 후에만 전송한다. 제출 허가는 merge/release/adopt 허가가 아니다. 기존 사용자 허가는 유효 범위 안에서 재사용한다.

제출 키는 destination/candidate ID/packet revision이며 payload digest와 함께 보존한다. timeout 후 marker/영수증을 조회하여 같은 전송을 재사용하고, 원격 상태를 볼 수 없으면 submission_unknown으로 남긴다. 동일 키의 다른 payload는 conflict다. 실패했다고 무조건 PR을 하나 더 만들지 않는다.

채택된 수정도 기존 태그를 바꾸지 않고 새 버전으로 배포한다. 프로젝트는 pin 상태를 유지하고 별도 diff·호환·복구 검토 후 적용한다. 새 이벤트가 생긴 뒤 과거 snapshot으로 전체를 덮지 않는다. 원래 오류의 재발·개입·비용을 재관측해야 루프가 닫힌다.

## 5. 대안 비교와 선택

| 방식 | 장점 | 비용·한계 | 판단 |
|---|---|---|---|
| v0.1.0 원칙 문서만 사용 | 시작 문맥과 관리 파일이 작음 | 후보·권한·스킬 관측·재적용 절차가 프로젝트마다 달라짐 | 간단한 수동 참고에는 유효 |
| 즉시 자동 업스트림 수정/승격 | 빠른 전파 가능성 | 공유 권한·중복 효과·일반성·rollback 실행기가 필요; 현재 증거 없음 | 현재 씨앗의 범위를 넘음 |
| contract 2의 작업 경계 검토 + 명시적 단계 | 같은 절차 재사용, 원자료 보호, 실패·권한·버전 추적, 추후 자동화 가능 | 23개 조항과 설정 관리가 추가되고 현재는 수동 수행 의존 | 현재 사용자 목표에 가장 적합한 설계 선택 |

선택 근거는 목표 적합성과 현재 구현 범위다. 처리시간·토큰 비용·오류율의 벤치마크 우위를 입증한 것은 아니다. 필요한 조항만 읽기, 한 번 검토, no_candidate, 기존 증거 참조로 문맥 부담을 제한한다. 실제 최적화 평가는 E02의 같은 workload·신뢰 하한·복잡도 지표로 수행해야 한다.

## 6. 상위/하위 계약 교차 감사

상위 RFC에서 세부 계약으로 내려가 의무를 확인하고, 세부 계약에서 상위 목표로 돌아가 불필요한 확장과 모순을 확인했다. 별도 독립 에이전트의 승인을 받았다는 의미는 아니다.

- 상위 승격 원칙과 후보 수집을 구별하여, 로컬 통과는 제출 가능 근거이고 범용 승격 증거는 아님을 명시했다.
- 초기 설계 유지보수와 경험적 승격을 구별하여 이번 계약 보완을 cross-domain 검증으로 오인하지 않게 했다.
- 스킬 사용과 실행 관측을 분리하고, 프롬프트 계약을 runtime enforcement로 표시하지 않게 했다.
- artifact 생성·release 영수증·deploy 관측을 분리했다. timeout과 projection 실패는 부작용 재실행 이유가 아니다.
- 계약 번호 읽기 지원과 실제 프로젝트 migration 호환을 분리했다. 설치 도구는 기존 기록을 덮지 않는다.
- 17개 목표에 개별 수락 시나리오를 연결하되 runtime 결과는 planned_not_executed로 유지했다.

## 7. 수락과 남은 실행 범위

배포 검사: 목표 누락/중복, 없는 조항 참조, 잘못된 runtime 검증 주장, 외부 권한 상속, 실제 기록이 채워진 예제를 거부한다. seed hash/inventory와 기존 설치의 dry-run/no-op/충돌/부분 실패 보호를 회귀 검사한다. 이는 자동 승격·권한 강제·canary·restore의 실행 검증이 아니다.

후속 runtime 구현에는 reducer/policy enforcement, 관측 collector, 승인된 submitter, 검증된 sandbox, rollout controller가 필요하다. 배포 저장소·실행 환경·예산·canary 수치가 실제로 필요해지는 시점에 인터뷰한다. 현재 공통 계약 배포를 위해 그 값을 추정하지 않는다.
