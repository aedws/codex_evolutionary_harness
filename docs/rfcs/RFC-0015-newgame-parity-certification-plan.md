# RFC-0015 — Newgame 기능 동등성을 확정하기 위한 실행 계획

TASK-20260915-PARITY-PLAN-001 / EXE-20260915-PARITY-PLAN-001

계획 작성일: 2026-09-15. 상태: 계획 초안 작성·범위 검토 가능. 구현·승격·외부 배포 승인이나 동등성 인증이 아니다.

## 1. 확정할 목표

Newgame에서 관찰할 수 있는 공통 하네스 기능을 재사용 가능한 씨앗에서 재현하고, 같은 입력·전제에서 같은 업무 결과와 동등하거나 더 엄격한 권한·실패 처리를 제공한다. `View to OOP, Set up to DOP`를 유지한다. 객체 수, 테스트 수, 문서 분량, HTML 일치는 완료 기준이 아니다.

오너가 선택한 검증 환경은 **별도 비공개 검증 프로젝트 → 검증된 씨앗 버전 → 현 프로젝트에 선택 적용**이다. 현 프로젝트의 오프라인 읽기 전용 결정은 유지한다. 이번 선택은 검증 환경의 방향이며 저장소 생성, 계정·자격증명 설정, 외부 쓰기·배포 권한을 자동으로 부여하지 않는다.

완료 판정을 세 개로 분리한다.

| 판정 | 확정하는 것 | 필요한 단계 |
|---|---|---|
| C1 공통 하네스 기능 동등성 | 고정된 Newgame 기능 목록의 입력·조회·행동·근거·권한·실패·복구 계약을 씨앗에서 재현 | P0~P7 모두 충족 및 오너의 정확한 범위 수락 |
| C2 현 프로젝트 선택 적용 | 선택한 기능이 AI-Agent-Execution-Platform에서 호환성·필수 검사·복구·가독성 조건 충족 | C1의 해당 기능 근거와 P8 |
| C3 계층 진화·최적화 검증 | Project→Domain→Core 일반화와 장기 신뢰/개입 감소 | P9; C1·C2 결과만으로 승격하지 않음 |

C1은 `고정 기준 be23c7c에 대한 범위 명시 공통 하네스 동등성`으로만 표현한다. 게임 전용 동작까지 포함한 “Newgame 전체 제품과 동일” 또는 “범용 V4 완성”이라고 표현하지 않는다. 원래 상위 목표의 계층 진화는 C3에서 계속 추적한다.

이 계획은 새 코드를 검사한 결과가 아니다. 기존 증거의 유효 범위를 재사용하며, 후속 변경은 새 snapshot과 필요한 회귀 검사로 판정한다.

## 3. 범위와 “같은 결과”의 정의 — P0에서 고정

참조 객체 257개와 관계 483개 각각에 대응 레코드를 둔다. 한 객체를 동일한 OOP 노드로 복제할 필요는 없지만, 목적·책임·원본·관계·행동·근거를 질의하는 기능이 사라져서는 안 된다. 예를 들어 문서·묶음은 문서 탐색, 원본은 Evidence/Source, 권한·담당은 Policy/Principal에서 조회할 수 있다. 위험·원칙은 원래 의미가 보존되는 프로젝트 확장 계약을 명시한다.

대응 레코드는 `reference_id, source_digest, target_ids, representation, supported_queries, case_ids, semantic_delta, decision_ref`를 가진다. 대응 없음·변환 손실·미검증은 별도 결과로 남긴다. 원본 자체에 없는 검증 증거를 정상값으로 만들어 채우지 않는다.

| 결과 축 | 비교 계약 |
|---|---|
| 객체·관계 | native ID 대응, 제목·목적·수락 조건, 관계 방향·유형·의미, 원본 탐색 가능성 |
| 상태 | 업무·실행 검사·인간 수락·배포를 분리. 원문 완료 선언과 실제 pass를 동일시하지 않음 |
| 행동 | 같은 전제와 허가에서 같은 효과/대상; 금지·취소·만료 시 효과 없음 |
| 증거 | 입력·룰·코드·원본·Run·출력 digest와 상태 생성 이유를 다시 추적 가능 |
| 실패 | 실패/불명/재시도/복구 분류와 다음 허용 행동; 조용한 데이터 손실이나 거짓 성공 없음 |
| 표현 | 같은 정보를 탐색·이해할 수 있음. 원본과 씨앗의 내부 저장 구조나 픽셀 일치는 요구하지 않음 |

결정적 출력은 승인된 ID/시간 필드 정규화 후 필드 단위 정확 일치로 비교한다. 타임스탬프·경로의 정규화는 미리 고정하고 상태·권한·실패 차이를 지우는 데 쓰지 않는다. 외부 서비스 결과는 고정 snapshot replay와 실제 호출 영수증을 구분한다. 비결정적 품질은 사전 수락 기준과 인간 평가로 판정한다.

Newgame 원문의 `implemented`를 씨앗 `verified`로 가져오지 않는 차이는 보호 원칙이다. 의도적 차이 목록과 그 수락 이유를 P0에서 오너가 고정한다. 나중에 실패한 필수 기능을 예외로 바꾸려면 범위 변경·새 평가가 필요하며, 기존 전체 동등성 판정을 유지하지 못한다.

게임 전용 Godot 실행·DPS/밸런스/맵 편집 동작(D01)은 Domain Pack 범위로 분리하는 안이다. 공통 하네스에서 이를 호출·검사·근거화하는 확장 경계는 범위에 포함한다. 오너의 범위 고정 전까지 이 제외안을 최종 승인으로 취급하지 않는다.

## 4. 단계별 계획

| 순서 / 단계 | 선행 조건 | 산출물과 통과 기준 | 실패 시 처리 |
|---|---|---|---|
| P0 범위·판정 기준 고정 | 현재 감사 근거 | F01~F20·D01의 필수/선택/도메인 분류, 257/483 대응 목록, 정상화 규칙, 권한·평가 주체·예외를 오너가 고정 | 미결정 항목은 필수 범위에서 임의 제외하지 않고 해당 판정 보류 |
| P1 비교 실행기·검증 프로젝트 설계/설치 | P0 | 비공개 검증 저장소·로컬 fixture·버전 manifest. 모든 필수 기능에 정상/실패/재실행/변경 입력/권한/복구 적용 여부와 case ID. 기존 씨앗 pass와 알려진 실패를 재현 | 기준 입력·grader 드리프트 또는 기대값 자체생성 발견 시 평가 중단 |
| P2 로컬 기능 공백 보완 | P1 | 전체 의미 대응, 관계·문서·결정·제안 초안·키보드/모바일 탐색. 모든 필수 로컬 질의·행동 case 통과; 보고서가 OOP 업무 노드로 중복되지 않음 | 기능별 미달 기록, 현재 배포 씨앗은 그대로 고정 |
| P3 권한·실행 경계 검증 | P1; P2 기능을 단계별 연결 | 검증용 독립 principal·최소 capability·만료/철회. UI뿐 아니라 직접 API/CLI의 자기승인·우회·재사용 허가·대상 변경 거부 | 실제 강제 근거가 없으면 documented_only; 보호된 실행 차단 |
| P4 외부 원본 adapter 검증 | P2+P3 및 원본별 읽기 범위 | Notion·Sheet의 별도 비민감 테스트 자료. ID/revision/observed_at/digest, 페이지 누락·삭제·중복·거부·부분 응답·오래된 snapshot·충돌 검사. 원본→수집→상태→위키 추적 | 마지막 snapshot을 stale/unknown으로 보존; 불명 응답을 삭제 또는 성공으로 처리하지 않음 |
| P5 PR·CI·배포 연결 | P3+P4, 정확한 검증 대상·예산 | 고정 commit의 필수 CI→불변 artifact→검증 대상 배포→health→영수증→위키. 실패한 CI·변조 artifact·잘못된 대상·불명 배포의 부정 검사 | 승격·활성화 중단; 같은 operation key로 상태 조회, 자동 재배포 금지 |
| P6 복구·이관·회수 훈련 | P5 | 아래 5종 복구를 격리 환경에서 실연. 코드·자료·원장·관계·활성 artifact 및 새로 생긴 기록 보존 확인 | rollback_pending/unknown; 이전 snapshot 덮어쓰기 대신 격리·전진 복구 검토 |
| P7 운영 Canary·C1 판정 | P0~P6 | 사전 확정 관찰 조건 충족, 필수 기능 전체 pass, 미해결 필수 공백 0, 독립 검토와 오너 범위 수락. 버전·대상·예외·한계를 포함한 C1 결과 | 관찰 부족은 inconclusive, 위반은 rejected/rollback_pending. 일부 pass로 전체 통과 금지 |
| P8 현 프로젝트 선택 적용·C2 | 해당 C1 근거+적용 대상 선택 | 변경 기능만 호환성 비교→새 경로 설치→기존 권한/원장 보존→프로젝트 필수 Run/위키 gate/회수 검사→오너 가독성 검수 | 해당 기능 회수 또는 pin 유지. 과거 승인 이관·외부 권한 확대를 적용 성공에 포함하지 않음 |
| P9 일반화·최적화·C3 | P7/P8 및 독립 프로젝트 자료 | 같은 도메인 독립 프로젝트 2개 이상, Core는 서로 다른 도메인 2개 이상; applicability/반례/holdout/비용·신뢰 평가. 해당 범위 승인 후 승격 | 로컬 성공은 로컬 후보로 유지. 표본 부족·공통 조상 오염·평가자 중복은 별도 표시 |

P2와 P3의 독립 구현 부분은 P1 이후 병행 설계할 수 있지만, 외부 효과는 P3 통과 전 실행하지 않는다. 이 계획은 에이전트 위임이나 예약 자동 실행을 생성하지 않는다.

## 6. 필수 실패·재실행·복구 계약

모든 case는 적용 가능한 아래 범주를 포함한다. 적용 불가면 근거와 검토자를 남기며 조용히 생략하지 않는다.

- 입력: 잘못된 schema/ID/경로, 중복·누락·순환, 소유권 충돌, 서로 다른 버전의 의미 충돌.
- 상태: 원본 변경·삭제, 오래된 검사, 충돌 결정, 제안자의 자기승인, 미검증/불명 상태의 거짓 승격.
- 권한: 허가 없음·철회·만료, 다른 대상·payload, 직접 API/CLI 우회, 숨긴 객체/관계/건수 노출.
- 효과: 동일 key/동일 입력은 영수증 재사용, 동일 key/변경 입력은 conflict, 완료 직후 응답 유실, 병행 요청, 중간 종료, 원격 성공 후 projection 실패.
- 복구: 읽을 수 없는 새 schema, 손상 백업, 부분 복구, rollback 실패, 복구 후 실제 신규 기록 보존.

복구 5종은 ① 파생 위키 재생성 ② 중단 실행의 관찰·reconcile ③ 코드/씨앗 회수 ④ 원장·자료 이관/복원 ⑤ 외부 효과 보상이다. 격리된 대상의 복구 후 ID/digest/관계/권한/행동을 대조하고, 백업 이후 생성된 사건이 남는지 확인한다. 백업 파일 존재나 Git 이전 commit 보유만으로 복구 통과를 선언하지 않는다.

권한 없는 효과·거짓 verified·중복 효과·이력 손실·인간 판단 침범은 **관찰된 사례 0건**이 필수다. 이는 절대 안전성의 통계적 증명이 아니다. 원본 Newgame에 같은 결함이 있어도 씨앗에서 허용하지 않는다.

## 7. Canary와 최적화의 판정 제안

아래 숫자는 **P0/P7에서 확정할 제안값**이며 이미 승인된 정책이나 보편적 충분 표본이 아니다.

- Canary 대상: 첫째 비공개 검증 프로젝트. 현 프로젝트는 P8에서 따로 편입한다. 초기에 원문 보유 내역·운영 자격증명·실사용자 데이터는 fixture로 사용하지 않는다.
- 최소 관찰: 7일과 완료된 업무 20건을 모두 충족. 조회/판단/수집/CI·배포/복구 strata를 사전 할당하고 빈 strata는 미검증으로 남긴다. 오래 걸리는 복구·저빈도 실패는 별도 장애 주입 사례로 기록한다.
- 중단: 신뢰 위반 1건, 예기치 않은 권한/효과, 호환성 실패, rollback 불가가 발견되면 영향 범위 확장 중지. 관찰 데이터 누락은 확대 보류이고 원격 효과는 unknown으로 유지한다.
- 확대: 관찰 창·case·필수 strata 충족, 미해결 필수 결함 없음, 복구 가능, 독립 검토 및 대상별 오너 결정이 모두 있어야 한다. 7일 경과만으로 자동 확대하지 않는다.
- 비용: 같은 workload·위험도·환경에서 기준/후보의 시간, 재시도, 문맥 사용량, 규칙 수+규범 텍스트 크기, 인간 개입 건수+분, 유지·복구 비용을 비교한다. 토큰 계측이 없으면 bytes로 명시하고 토큰 수를 추정해 인증하지 않는다.
- 최적화: 신뢰 위반 0과 결과 동등성을 먼저 충족. 예를 들어 사전 지정한 비용 지표 10% 이상 감소 및 다른 지표의 허용 악화폭 5% 이내를 제안한다. 정확한 지표·표본·변동성/신뢰구간·허용폭은 결과 관찰 전에 고정한다. 불충분한 표본이면 inconclusive이며 “더 최적화됨”을 선언하지 않는다.

외부 호출 횟수·비용·보관 기간·CI runner·hosting 자원은 각 검증 계획에서 산정한다. 기존 Claude/금융 API 예산을 이 검증의 예산으로 재사용하지 않는다. 무료 제공 범위도 실행 시점의 실제 계정/서비스 조건을 확인하고, 미확정 유료 사용은 시작하지 않는다.

## 8. 권한·파일 소유권·판정 영수증

제안자는 코드/후보를 작성하고, 평가자는 고정 candidate/fixture/grader로 결과를 생성한다. 오너 또는 별도로 지정된 승인자가 정확한 diff·평가·대상 범위를 수락한다. 효과 실행자는 해당 결정만 수행한다. 동일 에이전트의 재서술이나 이름만 다른 계정을 독립 평가로 세지 않는다. 독립 인력이 없으면 독립 수락은 미충족으로 표시한다.

씨앗은 공통 schema/CLI/검증·생성 규칙과 빈 adapter 계약을 소유한다. 검증 프로젝트는 비민감 fixture·권한·대상·실행 영수증을 소유한다. 현 프로젝트는 원문 자료·업무 객체·overlay·로컬 원장·오너 결정을 소유한다. 생성 위키는 파생물이고 수동 원본을 덮어쓰지 않는다. 테스트 자료를 씨앗에 올릴 때도 별도의 공유 범위 확인이 필요하다.

판정 영수증은 최소한 다음을 가진다.

```text
claim_id / claim_scope / reference_commit / seed_digest / overlay_digest
environment_digest / source_snapshot / case_set_digest / grader_digest
proposer / evaluator / approver / authority_refs / overlap_disclosure
case_results / raw_evidence_refs / failed_and_deferred_attempts
intentional_differences / exceptions / compatibility / recovery_proof
canary_target / observation_window / observation_completeness
verdict / reasons / accepted_scope / expiry_or_invalidation_triggers
```

최종 verdict는 accepted_for_scope, rejected, inconclusive 중 하나다. 작성자가 임의로 상태 필드를 설정하는 방식은 사용하지 않고 근거·규칙·승인에서 파생한다. 기준 source/manifest·중요 정책·schema·grader·필수 adapter·범위가 바뀌면 영향받는 claim을 stale로 돌리고 해당 gate를 다시 적용한다. 변경 영향이 없는 이전 증거는 정확한 범위에서만 재사용한다.

## 9. 시작 순서와 인터뷰 지점

바로 다음 구현 작업의 범위는 **P0 상세 case manifest와 P1 오프라인 비교 실행기**다. 이번 요청은 그 작업을 위한 계획 작성이며 실행 코드나 검증 저장소를 생성하지 않는다.

P0 인터뷰에서는 공통 하네스/게임 Domain 범위, 보호 원칙에 따른 상태 차이, 독립 검토자를 확정한다. P3 직전에는 검증 프로젝트의 역할·계정·쓰기 범위를, P4 직전에는 Notion/Sheet 원본 식별자·읽기 범위·신선도 기준을, P5 직전에는 비공개 GitHub/CI/hosting 대상·비용·보관·회수 권한을 구체화한다. P7 직전에는 관찰 기간·업무 표본·중단/확대 판단자를 확정한다.

필요한 질문은 해당 결과와 권한 차이를 검토할 수 있을 때 한 묶음으로 요청한다. 이미 정한 현 프로젝트의 오프라인 모드나 이번 비공개 검증 환경 선택은 반복 질문하지 않는다. 대기 중에도 외부 효과가 없는 fixture·계약·검사 설계는 진행할 수 있다.

날짜 기반 완료를 약속하지 않는다. P0~P6은 gate 단위로 진행하고, 외부 계정/대상 확보와 P7 관찰 창이 일정의 선행 조건이다. 현 시점에서 “모든 기능이 확정되는 날짜”는 unknown이다.

## 10. 현재 요청의 완료 조건

계획 문서, F01~F20·D01 전수 매핑, 단계 의존성, 수락/중단/회수 조건, 오너 결정 지점, 기존 증거·권한 경계가 빠짐없이 연결돼 있으면 **계획 작성 완료**다. 이는 P0 범위 승인, P1~P9 실행 완료, C1~C3 인증이 아니다.

이 문서의 계획 원본은 씨앗 저장소에 둔다. 현 프로젝트의 이미 검증된 원장·코드·위키 생성 입력은 이번 계획 작성으로 변경하지 않는다. 후속 구현을 시작할 때 관련 계획 Task와 계약 보고서를 프로젝트 위키에 등록하고 그 변경의 필수 gate를 함께 수행한다.
