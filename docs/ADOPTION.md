# 범용 프로젝트 적용과 최종 목표 도달 조건

현재 v0.3.0 / contract 3을 내려받는 것만으로 최종형 Evolutionary Agentic SDLC가 완성되지는 않는다. 공통 규격을 도입하고 사람/에이전트가 증거 기반 절차를 수행할 출발점은 제공한다. 자동 상태 계산·권한 강제·개선 평가·계층 승격·Canary 전파는 추가 구현과 실제 운영 증거가 필요하다.

## 1. 무엇이 공급되고 무엇을 프로젝트가 채워야 하는가

| 단계 | 현재 씨앗 | 프로젝트에서 필요한 일 / 달성 근거 |
|---|---|---|
| 공통 출발점 | 버전 고정 설치, 빈 기록, 공통 계약 | 설치 영수증과 파일 hash 확인; 기존 정책은 검토 통합 |
| Project 특화 | 빈 overlay, source-authority와 bootstrap 절차 | 목표·도메인·원본·도구·검사·권한·인간 수락을 실제 출처로 바인딩 |
| OOP View / DOP 운영 | 객체·관계·이벤트·증거와 checkpoint 계약 | 첫 실제 Task→Execution→Evidence→Event→checkpoint 연결; 수동 파생임을 표시 |
| 전체 위키와 설명 가능한 View | 탐색·권한·claim 계보 계약 | 프로젝트 정보구조와 source adapter, renderer/generator 구현·관측; 현재는 Markdown부터 사용 |
| V2 신뢰 기반 | 상태·정책·복구 요구사항 | validator/reducer·실행 gate·재생/복구 구현 및 false_verified/우회/중단 검증 |
| V3 프로젝트 자기개선 | 오류·스킬 관측, 후보·평가 절차와 빈 예제 | 관측 수집·동결된 baseline/candidate eval·권한 있는 적용·원래 오류 재관측; 자동화는 별도 실행기 필요 |
| V4 계층 진화 | 일반화·교차 평가·승격·전파 계약 | 독립 프로젝트/도메인 증거, 승인 주체, 공유 권한, 호환/Canary/회수 controller와 실제 적용 결과 |
| 더 높은 신뢰와 더 적은 개입 | 비교 지표와 판정 계약 | 같은 workload의 신뢰 하한·전체 context·사람 시간·회귀/복구 비용을 실측 |

`verified_capabilities`와 `automated_enforcement`는 현재 빈 배열이다. 계약 3이라는 숫자는 V3 능력의 인증이 아니다. 최종 목표에 대한 설계 경로는 있지만, 단일 프로젝트의 설치 성공은 여러 도메인에서의 일반화 증거가 될 수 없다.

## 2. 첫 프로젝트의 사용 순서

1. [README 사용법](../README.md)으로 고정 태그의 씨앗을 별도 프로젝트에 설치한다. 기존 파일 충돌이면 임시 설치본과 비교해 통합한다.
2. 대상 프로젝트를 에이전트의 작업 폴더로 열고 `BOOTSTRAP_PROMPT.md`의 bootstrap을 명시적으로 요청한다. 파일 존재만으로 자동 시작하거나 모든 에이전트가 지침을 읽는다고 가정하지 않는다.
3. 목표·수락 조건·원본 권위·필수 검사·작업 범위를 조사한다. 확인된 내용만 overlay에 넣고 미확정 항목은 unknown 또는 필요한 인터뷰로 남긴다. 도메인 이름을 임의로 결정하지 않는다.
4. 승인된 첫 실제 작업을 작게 수행한다. 검사가 대상 코드/데이터 버전에 연결됐는지, 이벤트와 checkpoint의 주장에 근거가 있는지 확인한다. 테스트가 없으면 검증 통과로 표시하지 않는다.
5. 작업 경계에서 오류·마찰·스킬 사용 결과를 검토해 candidate/deferred/no_candidate를 기록한다. 공통 개선 후보는 원자료를 보존하고 재현 가능한 추상 문제로 정리한다.
6. 필요한 경우에만 upstream 목적지·정확한 공유 범위·제출 권한·평가 예산을 정한다. 승인된 제출과 maintainer의 merge/release는 별개다. 제출 설정이 비어 있으면 로컬 운영을 계속한다.
7. 새 씨앗 릴리스는 프로젝트가 pin을 유지한 상태에서 호환·복구 검토 후 적용한다. 원래 오류와 전체 비용을 다시 관측해야 피드백 루프가 닫힌다.

한 사람이 이 절차를 수동 운영하는 것은 가능하지만, 이를 이미 구현된 자율 실행기로 표시하지 않는다. 여러 에이전트를 쓰더라도 같은 입력을 반복한 것만으로 독립 프로젝트 평가가 되지 않는다.

## 3. 범용성의 범위

배포기는 표준 Python으로 허용된 문서·JSON 파일을 복사한다. 제품의 언어·프레임워크·게임 엔진을 선택하거나 앱 의존성을 설치하지 않는다. 따라서 Python·JavaScript·데이터 중심 프로젝트처럼 서로 다른 파일 구성을 공통 규격으로 시작할 수 있도록 설계되어 있다. 실제 빌드/데이터 검증/배포 명령과 수락 조건은 프로젝트가 제공해야 한다.

새 내려받기와 대표 파일 구성에 대한 설치·기존 파일 보존·재실행·지침 충돌 검사는 [이번 실행 증거](harness/evidence/EXE-20260913-ADOPTION-001/validation.json)에 기록한다. 이 검사는 합성 fixture의 파일 배치 호환성만 다룬다. 해당 언어 앱의 실행, 실제 제품 성과, 모든 운영체제, 장기 자기개선 또는 교차 도메인 일반화 검증은 아니다.

현재 실행 검증 환경은 Windows의 Python 3.13이다. 배포 코드의 Python 3.10+ 요구사항과 운영체제별 실제 검증 결과는 구분한다. Linux/macOS에서는 경로와 Python 실행 이름을 조정하고 그 환경에서 별도 확인해야 한다.

## 4. 최종 목표를 완료로 판단하기 위한 조건

V2는 실제 증거/파생/권한/복구 메커니즘의 시험과 운영 관측, V3는 같은 프로젝트의 baseline 대비 신뢰·개입·전체 비용 비교, V4는 독립 프로젝트와 여러 도메인에서의 승격 및 안전한 하향 적용 관측을 요구한다. 인간 판단이 필요한 수락 조건은 별도 인간 결정으로 남긴다.

새로운 목표 문구나 템플릿을 더 추가하는 것으로 이 간격이 없어지지는 않는다. 다음 구현 단계는 파일 저장/검증/파생·도구 gate·실제 프로젝트 adapter를 갖춘 최소 V2 실행 경로를 별도 범위로 정하고, 한 실제 작업에서 끝까지 관측하는 것이다. 이후 결과에 따라 V3/V4를 확장한다. 이번 작업은 그 구현에 대한 자동 승인이 아니다.
