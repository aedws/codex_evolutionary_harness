# 범용 프로젝트 적용과 최종 목표 도달 조건

현재 v0.6.1 / contract 6는 공통 계약과 최소 로컬 실행 코어를 제공한다. 설정된 검사 실행, 버전에 결합된 관측, 이벤트 기반 상태 설명, 로컬 개선 후보와 원장 복원을 실제로 수행한다. 설치만으로 최종형 Evolutionary Agentic SDLC가 완성되지는 않는다. 실제 프로젝트 바인딩과 운영 결과, 독립 평가·승격·Canary 구현이 더 필요하다.

## 1. 무엇이 공급되고 무엇을 프로젝트가 채워야 하는가

| 단계 | 현재 씨앗 | 프로젝트에서 필요한 일 / 달성 근거 |
|---|---|---|
| 공통 출발점 | 버전 고정 설치, 빈 기록, 공통 계약 | 설치 영수증과 파일 hash 확인; 기존 정책은 검토 통합 |
| Project 특화 | 빈 overlay, source-authority와 bootstrap 절차 | 목표·도메인·원본·도구·검사·권한·인간 수락을 실제 출처로 바인딩 |
| OOP View / DOP 운영 | 객체·관계·이벤트·증거와 checkpoint 계약 | harness.py의 Task→Run→Event→status/view 연결; 그 밖의 수동 파생은 표시 |
| 전체 위키와 설명 가능한 View | 탐색·권한·claim 계보 계약 | 프로젝트 정보구조와 source adapter, renderer/generator 구현·관측; 현재는 Markdown부터 사용 |
| V2 신뢰 기반 | 엄격한 로컬 원장·상태 계산·고정 명령 gate·백업/별도 복원 | 실제 프로젝트 검사 바인딩·운영 검증, 외부 adapter·OS/신원 권한 분리 |
| V3 프로젝트 자기개선 | 오류·스킬 관측, 후보·평가 절차와 빈 예제 | 실행 관측에서 candidate CLI로 로컬 제안 기록; 동결된 baseline/candidate eval·권한 있는 적용·원래 오류 재관측은 별도 운영/구현 |
| V4 계층 진화 | 일반화·교차 평가·승격·전파 계약 | 독립 프로젝트/도메인 증거, 승인 주체, 공유 권한, 호환/Canary/회수 controller와 실제 적용 결과 |
| 더 높은 신뢰와 더 적은 개입 | 비교 지표와 판정 계약 | 같은 workload의 신뢰 하한·전체 context·사람 시간·회귀/복구 비용을 실측 |

`verified_capabilities`는 전체 V2/V3/V4 인증을 주장하지 않아 빈 배열이다. `automated_enforcement`는 로컬 검사 dispatch와 bootstrap_readiness_gate를 선언한다. 계약 5라는 숫자는 V4 능력의 인증이 아니다. 최종 목표에 대한 설계 경로는 있지만, 단일 프로젝트의 설치 성공은 여러 도메인에서의 일반화 증거가 될 수 없다.

## 2. 첫 프로젝트의 사용 순서

1. [README 사용법](../README.md)으로 고정 태그의 씨앗을 별도 프로젝트에 설치한다. 기존 파일 충돌이면 임시 설치본과 비교해 통합한다.
2. 대상 프로젝트를 에이전트의 작업 폴더로 열고 `BOOTSTRAP_PROMPT.md`의 bootstrap을 명시적으로 요청한다. 파일 존재만으로 자동 시작하거나 모든 에이전트가 지침을 읽는다고 가정하지 않는다.
3. 목표·수락 조건·원본 권위·필수 검사·작업 범위를 조사한다. 확인된 내용만 overlay에 넣고 미확정 항목은 unknown 또는 필요한 인터뷰로 남긴다. 도메인 이름을 임의로 결정하지 않는다.
4. 제품 작업 전에 V01/V03에 따라 전체 프로젝트 위키를 통합/구성하고 [bootstrap Gate](../seed/docs/harness/bootstrap/README.md)를 필수 검사에 연결한다. 최종 bootstrap_ready는 위키 구조/출처/관계/역할 경로와 현재 검증 Run이 모두 있어야 한다. 인간 수락은 별도다. [로컬 코어 사용법](../seed/docs/harness/runtime/README.md)에 따라 실제 policy/task를 준비하고 init→task→run→status/view를 실행한다. 승인된 첫 실제 작업을 작게 수행한다. 검사가 대상 코드/데이터 버전에 연결됐는지, 이벤트와 checkpoint의 주장에 근거가 있는지 확인한다. 테스트가 없으면 검증 통과로 표시하지 않는다.
5. 작업 경계에서 오류·마찰·스킬 사용 결과를 검토해 candidate/deferred/no_candidate를 기록한다. 공통 개선 후보는 원자료를 보존하고 재현 가능한 추상 문제로 정리한다.
6. 필요한 경우에만 upstream 목적지·정확한 공유 범위·제출 권한·평가 예산을 정한다. 승인된 제출과 maintainer의 merge/release는 별개다. 제출 설정이 비어 있으면 로컬 운영을 계속한다.
7. 새 씨앗 릴리스는 프로젝트가 pin을 유지한 상태에서 호환·복구 검토 후 적용한다. 원래 오류와 전체 비용을 다시 관측해야 피드백 루프가 닫힌다.

로컬 코어는 검사·관측·판정을 실행하고, 나머지 절차는 권한 있는 사람이 운영한다. 전체 자율 진화가 구현됐다고 표시하지 않는다. 여러 에이전트를 쓰더라도 같은 입력을 반복한 것만으로 독립 프로젝트 평가가 되지 않는다.

## 3. 범용성의 범위

배포기는 표준 Python으로 manifest에 고정된 문서·JSON·독립 Python 코어를 복사한다. 제품의 언어·프레임워크·게임 엔진을 선택하거나 앱 의존성을 설치하지 않는다. 따라서 Python·JavaScript·데이터 중심 프로젝트처럼 서로 다른 파일 구성을 공통 규격으로 시작할 수 있도록 설계되어 있다. 실제 빌드/데이터 검증/배포 명령과 수락 조건은 프로젝트가 제공해야 한다.

v0.3.0에서 수행한 대표 파일 구성의 설치·기존 파일 보존·재실행·지침 충돌 검사는 [이전 실행 증거](harness/evidence/EXE-20260913-ADOPTION-001/validation.json)에 기록한다. 이 검사는 합성 fixture의 파일 배치 호환성만 다룬다. 해당 언어 앱의 실행, 실제 제품 성과, 모든 운영체제, 장기 자기개선 또는 교차 도메인 일반화 검증은 아니다.

현재 실행 검증 환경은 Windows의 Python 3.13이다. 배포 코드의 Python 3.10+ 요구사항과 운영체제별 실제 검증 결과는 구분한다. Linux/macOS에서는 경로와 Python 실행 이름을 조정하고 그 환경에서 별도 확인해야 한다.

## 4. 최종 목표를 완료로 판단하기 위한 조건

V2는 실제 증거/파생/권한/복구 메커니즘의 시험과 운영 관측, V3는 같은 프로젝트의 baseline 대비 신뢰·개입·전체 비용 비교, V4는 독립 프로젝트와 여러 도메인에서의 승격 및 안전한 하향 적용 관측을 요구한다. 인간 판단이 필요한 수락 조건은 별도 인간 결정으로 남긴다.

사용자의 “최소 실행 코어까지 구현하고 검증” 승인에 따라 로컬 실행 경로를 추가했다. [RFC-0005](rfcs/RFC-0005-end-to-end-decision-system.md)는 8개 판정 계약과 16개 단계의 의존성을 연결한다. 다음 운영 단계는 사용자 프로젝트의 실제 검사와 수락 조건을 바인딩하고 원래 오류의 개선·회귀·개입 비용을 관측하는 것이다. 교차 프로젝트 평가, 인증된 역할 분리, 실제 Canary는 별도 구현과 증거가 필요한 후속 게이트다. 데이터가 없는 단계는 unknown/unverified로 남겨야 한다.

최소 코어의 실제 하위 프로세스 실행·실패/재시도·정책 변경·동시 실행·설치본 CLI·복원 검증은 [v0.4.0 실행 증거](harness/evidence/EXE-20260913-DECISION-001/validation.json)를 따른다. 합성 제품의 실행을 포함하며 실제 사용자 제품의 운영 성과를 대신하지 않는다.
