# Fixed V2 project operating contract

Read `docs/harness/README.md`, `source-authority.md`, `policy.md`, then `checkpoint.md` in that directory. Load task-relevant sources only. The distributed `core.py`, `harness.py`, `wiki.py` are fixed executables: do not recreate, patch or replace them to make a project pass.

View to OOP, Set up to DOP. Requirement / Task / Decision / Module / Test / Release are human interfaces. Events, test observations, inputs, config IDs and eval results generate their state. Narration never proves verification. Installation generates an object wiki draft immediately; bind real project sources and inspect `wiki/index.html` before product work. Do not create a report node for every execution; keep evidence under the stable object and group objects by derived state.

Query/analysis is read-only; plan may register work, execute implements only granted scope. First interview the owner for goal, authoritative input files, trusted test adapter, model context, roles and exposure. This implementation supports an offline single-owner local workspace with no login. It has separate proposer/evaluator/owner operator labels, not authenticated human identity. A future hosted system requires a new reviewed adapter and authorization; no default remote exposure.

Start from V2. Register stable Task and one operation key per logical command, run the actual tests, classify observations, record a checkpoint and resume from evidence. Use the CLI contract; do not edit `.harness/ledger.sqlite3`. Keep unknown/stale/blocked outcomes. Machine test pass is separate from human MVP acceptance.

Observe from day one. Expression preference, product correctness, authority violation, workflow friction, skill change and unknown remain distinct. Bugs and authority violations must not become preference overlays. At a task boundary review feedback once under `docs/harness/contracts/feedback.md`.

Checkpoint checks readiness and may generate a bounded isolated candidate. Readiness is not V3 adoption. Only allowed presentation/navigation/alias fields may vary. Permissions, retention, source authority, acceptance and deployment rules cannot change through habits. `next` or an alias returns at most one explicitly scoped task; it does not grant implementation, commits, deployment or external effects.

Compare against the frozen active baseline using the preregistered suite. A different evaluator label evaluates once; owner records an explicit adoption decision. Insufficient evidence/no improvement means V2 remains normal. V3 is frozen for the named project/model/eval conditions, not globally optimal. In-flight tasks keep their original config. Reopening requires a new candidate, never editing a frozen config. Core/domain promotion is a separate reviewed release with cross-project evidence; not automatic.

Commit, push, merge, deploy, paid calls, external writes and credentials require explicit authorization unless already granted for this task. Preserve authority across turns. This seed grants none by default. Never weaken history, rollback or test oracles to pass a gate. Local test subprocesses are trusted programs, not an OS sandbox.

Completion: changed; verified; unverified/stale; blocked; evidence/events; external effects; feedback; next allowed action. Mention the tested scope rather than declaring full harness/product completion.
