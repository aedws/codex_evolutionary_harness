# 고정 V2 씨앗 사용법

배포 버전 **2.0.0-dev.1**, 계약 `fixed-v2-1`. V2/V3는 운용 단계이며 패키지 버전과 다릅니다.

1. 설치 직후 `wiki/index.html`을 열어 대문 → 주제 6개 → 객체 구조를 확인합니다. 아직 프로젝트 연결은 미검증입니다.
2. 오너 인터뷰로 목적, 원본 파일, 실제 검사 스크립트, 역할, 모델 조건, 오프라인 범위를 결정합니다. `examples/`는 합성 데모이며 프로젝트의 사실이 아닙니다.
3. JSON 설정을 준비해 `python -B harness.py init --data setup.json --actor owner --key init-001`을 실행합니다. [CLI 계약](contract.md)의 정확한 필드를 사용합니다.
4. Requirement/Module 원본을 `object`로 연결하고, `task` → 구현 → `run`으로 실제 검사합니다. 실행 결과와 파일 hash가 원장에 기록됩니다.
5. `observe`로 관측을 분류하고, `resume`으로 근거를 다시 읽습니다. 기본 사용자 흐름은 오너가 `mvp`로 수락합니다. 테스트 통과만으로 인간 판단을 대신하지 않습니다.
6. `checkpoint`가 준비 조건을 판정합니다. 조건을 충족하면 제안된 허용 필드에서 예산 내 후보가 자동 생성됩니다. 후보는 운용 구성을 바꾸지 않습니다.
7. evaluator가 `evaluate`, owner가 `adopt`를 실행하면 검증 범위의 V3가 고정됩니다. 실패/개선 없음/자료 부족이면 V2 유지가 정상입니다.

`python -B harness.py view`는 상태 JSON, `wiki`는 읽기 전용 HTML, `audit`는 이벤트와 판정 근거를 출력합니다. 모든 변경 명령은 `--data JSON --actor LABEL --key LOGICAL_OPERATION_ID`가 필요합니다. 동일 key+내용 재시도는 동일 receipt를 반환하며 새로운 검사로 취급되지 않습니다.

현재 평가기는 **명령 해석 정확도·권한 회귀**를 고정 사례로 비교합니다. 표현·문맥 순서·체크리스트 필드는 적용 가능하지만 그 품질 개선만으로 자동 채택되지는 않습니다. 실제 LLM 후보 생성, 사용자 경험 일반화, OS/원격 인증, 외부 배포 및 상위 승격은 구현 범위 밖입니다. 프로젝트별 실행기를 AI가 새로 만드는 방식은 사용하지 않습니다.

운용 흐름: **V2 → 기반 루프·관측 → 준비 → 후보 → 비교 → V3 고정**. 객체·증거·이벤트 모델과 전환 로직은 배포본에 고정됩니다.
